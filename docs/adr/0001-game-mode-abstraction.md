# Game modes are objects with pure hooks over a discriminated match state

Siege is a second way to decide a match, so match-level transitions (start, goal, shot consumed, winner) move out of the step function into a game mode object with pure hooks that return match state plus events. Match state is a union keyed by `mode`, and the sim config names the mode. The step function keeps physics, possession, build turns and the shot clock.

## Considered Options

- **A mode string with branches inside step.** Rejected: every new mode adds if-branches through the step function.
- **Separate step functions sharing physics helpers.** Rejected: possession, shot clock and build turn logic would be duplicated or threaded through helpers, and lockstep determinism would have two paths to keep in sync.
- **Mode object with pure hooks (chosen).** One step function; a mode implements `start`, `onShotFired`, `onShotConsumed`, `onGoal`, `onBuildDone`, `onBuildTimeout`, `onBuildStart`, `onDefenceChoice`, `choiceTimeout`, `mayEdit`, `mayRefund`, `maySubterfuge`, `hasCredits`, `paysTowers`, `paysBreaker`, `mayPlayBuild`, `opening` and `winner`. The hooks that judge the board (`onShotConsumed`, `onGoal`, `onBuildDone`, `onBuildTimeout`, `onBuildStart`, `onDefenceChoice` and `winner`) also get a read-only context (`objects`, `possession`, `shooter`, who took the shot being resolved even if possession has since passed on, and `credits`, what each player holds before the hook's result is applied) so a mode can judge the board without branches in step; `start`, `onShotFired`, `choiceTimeout`, `mayEdit`, `mayRefund`, `maySubterfuge`, `hasCredits`, `paysTowers`, `paysBreaker`, `mayPlayBuild` and `opening` read only the match. `mayRefund` says whether the shooter may trade Move points for Credits (ADR-0004), so step needs no Siege branch for it. `maySubterfuge` says whether a player may buy Subterfuge items with Credits (none in Siege, which has no Credits economy), `paysTowers` whether towers cost Credits (`rules.towerCost`) rather than coming from the fixed stock (Siege), and `paysBreaker` whether the Breaker costs Credits (`rules.breakerCost`) rather than coming from the 3-each stock (Siege). `mayPlayBuild` says whether the shooter may still place pieces in play (an in-play build, at `rules.playBuild` prices): Rounds before the round's first shot, never in Siege. `hasCredits` says whether the mode has a Credits economy at all (the Resource bar shows only where it does); it sits on `GameMode` because it states a fact about the mode's economy (ADR-0004), not a view concern, so the presentation layer reads it instead of switching on the mode name. `onBuildDone` may refuse (null) and emit events; `onBuildTimeout` names a fallback piece for a builder whose timed-out Done was refused, so the build timer still bounds the turn; `onBuildStart` says what a new build turn looks like (the builder's Credits, given what they hold, and which structures are movable) and `mayEdit` whether it may place and demolish at all, so a Rearrange turn (movable pieces, no placing, no demolish) needs no branch in step. `opening` says whether a build turn is the blind opening build (as opposed to a Rearrange); the fog and the reveal key on it through `openingBuild` and `blindSeat` in `mode.ts`. Step calls `winner` whenever a shot is consumed or a goal is scored, whether or not the hook returned a result, and ends the match itself. `choiceTimeout` names what the sim picks for a chooser when the build window runs out while the choice is pending (Siege: Repair), so the timer needs no Siege branch in step. `onDefenceChoice` resolves a defence choice from the player the match is waiting on (null refuses); a hook result may also replace `objects` (a repair).
- **A generic hold: `match.choosing`.** Siege's `onGoal` names the scorer in `choosing` (on the shared match fields, not in Siege-only state) and step holds play while it is set: no shots, no ball placement, no shot clock, and a `defence` input only from that player. Under a build timer the hold runs the build window instead (opened at the goal, drained while it is pending, expiry synthesises the `choiceTimeout` choice, and a turn opened by a choice continues the window rather than refilling it). It lives on the base so step can gate on it without knowing the mode; step clears it when the match ends.

## Consequences

- Rounds behaviour is unchanged; its logic lives in `src/sim/mode.ts`.
- Reading per-mode match fields (round, score) requires narrowing on `match.mode`.
- A new mode adds a union member, a hooks object and an entry in the `MODES` record in `mode.ts` (which `modeFor` and `modeNamed` both read), not branches in step. Step dispatches through `modeFor(state.match)`; only `initialState` reads `config.mode`.
- The sim and its rules are fully behind the hooks, but the presentation layer still switches on the mode name in six switches and one exhaustive record, each of which a new mode must also edit: `slidersFor` and `sliderLabel` (`settings.ts`, which sliders the settings screen shows and what the Opening Credits slider is called), `sliderDefault` (`settings.ts`, a slider's per-mode default), `digitsOf` and `roundOf` (`game/view/hudModel.ts`, the per-player digit on `HudModel` (Rounds' score, Siege's structure count) and the round number that also drives the first-play hint), `resultOf` (`game/Game.ts`, the end-screen text), and the `UNITS` record (`game/view/units.ts`, the name of the builder's balance: `menu` beside a number in the Side menu, `chip` on the balance chip and the Strategy cards, `CR` or `PTS`; it sits in `game/view`; no `src/ui` file imports it: the chip form reaches `src/ui` through `HudModel.balance.unit`, the menu form through the Side menu rows' pre-formatted text). They are exhaustive, so the compiler points at each one. They were left as switches rather than moved onto `GameMode` because the hooks are pure sim state transitions, and these are view concerns that would drag HUD and screen strings into the sim.
- The hooks must stay pure so the sim remains deterministic for lockstep.
